3. What are indexes in PostgreSQL, and why are they important?

Answer:
Indexes in PostgreSQL are special lookup tables that the database search engine uses to speed up data retrieval. Simply put, an index is a pointer to data in a table. Indexes are important for improving the speed of data retrieval operations on a database table at the cost of additional writes and storage space to maintain them.

4. Explain the VACUUM command in PostgreSQL. Why is it used?

Answer:
The VACUUM command is used to reclaim storage occupied by dead tuples (rows). In PostgreSQL, when rows are updated or deleted, the old versions of the rows are not physically removed during the transaction; instead, they are marked as dead. VACUUM cleans up these dead tuples, making space available for future use and preventing table bloat. Regular use of VACUUM is crucial for removing these obsolete rows and maintaining database performance.

Describe the different types of JOINs available in PostgreSQL.

Answer:
PostgreSQL supports several types of JOINs, including:

INNER JOIN: Returns records that have matching values in both tables.
LEFT OUTER JOIN: Returns all records from the left table, and matched records from the right table; if there is no match, the result is NULL on the side of the right table.
RIGHT OUTER JOIN: The opposite of LEFT JOIN, returning all records from the right table, and matched ones from the left.
FULL OUTER JOIN: Combines LEFT and RIGHT JOIN, returning records when there is a match in one of the tables.
CROSS JOIN: Returns the Cartesian product of both tables.
7. Explain how PostgreSQL uses MVCC (Multi-Version Concurrency Control).

Answer:
MVCC in PostgreSQL is used to control data consistency when multiple transactions are occurring concurrently without locking the data. Instead of overwriting live data, PostgreSQL keeps past versions of a row in the same table, which allows for "time travel" within the database and querying an older snapshot of the database, thus increasing concurrency and performance.

8. How does PostgreSQL handle replication and what are the types of replication available?

Answer:
PostgreSQL handles replication by streaming changes from a primary server to one or more secondary servers. Replication can be synchronous or asynchronous. In synchronous replication, the primary waits for confirmation from the secondary server before committing a transaction, ensuring no data loss. In asynchronous replication, the primary does not wait, which can lead to faster performance but at the risk of potential data loss.

9. Discuss partitioning in PostgreSQL. Why is it used and what are the benefits?

Answer:
Partitioning in PostgreSQL involves splitting a large table into smaller, more manageable pieces, while keeping the structure of the data intact. It is used to improve query performance, manage large tables, and assist in quicker data access for specific queries based on partition keys. The benefits include improved query performance, easier management of large datasets, and enhanced data retention strategies.

7. JOINS - RELATIONSHIPS BETWEEN TABLES
================================================================================

-- INNER JOIN (only matching records)
SELECT * FROM table1 INNER JOIN table2 ON table1.id = table2.table1_id;
SELECT * FROM table1 JOIN table2 ON table1.id = table2.table1_id;  -- Same as INNER

-- LEFT JOIN (all from left table + matching from right)
SELECT * FROM table1 LEFT JOIN table2 ON table1.id = table2.table1_id;

-- RIGHT JOIN (all from right table + matching from left)
SELECT * FROM table1 RIGHT JOIN table2 ON table1.id = table2.table1_id;

-- FULL OUTER JOIN (all records from both tables)
SELECT * FROM table1 FULL OUTER JOIN table2 ON table1.id = table2.table1_id;

-- CROSS JOIN (Cartesian product)
SELECT * FROM table1 CROSS JOIN table2;

-- SELF JOIN (joining table with itself)
SELECT a.column1, b.column2 FROM table1 a, table1 b WHERE a.id = b.parent_id;

-- Multiple table joins
SELECT * FROM table1 
JOIN table2 ON table1.id = table2.table1_id 
JOIN table3 ON table2.id = table3.table2_id;

8. SUBQUERIES AND NESTED QUERIES
================================================================================

-- Subquery in WHERE clause
SELECT * FROM table1 WHERE column1 IN (SELECT column1 FROM table2);
SELECT * FROM table1 WHERE column1 = (SELECT MAX(column1) FROM table2);

-- Subquery in SELECT clause
SELECT column1, (SELECT COUNT(*) FROM table2 WHERE table2.id = table1.id) AS count 
FROM table1;

-- Subquery in FROM clause (derived table)
SELECT * FROM (SELECT * FROM table1 WHERE condition) AS derived_table;

-- EXISTS and NOT EXISTS
SELECT * FROM table1 WHERE EXISTS (SELECT 1 FROM table2 WHERE table2.id = table1.id);
SELECT * FROM table1 WHERE NOT EXISTS (SELECT 1 FROM table2 WHERE table2.id = table1.id);

-- ANY and ALL
SELECT * FROM table1 WHERE column1 > ANY (SELECT column1 FROM table2);
SELECT * FROM table1 WHERE column1 > ALL (SELECT column1 FROM table2);

10. WINDOW FUNCTIONS (Advanced Analytics)
================================================================================

-- ROW_NUMBER() - assigns unique number to each row
SELECT *, ROW_NUMBER() OVER (ORDER BY column1) AS row_num FROM table_name;

-- RANK() - assigns rank with gaps for ties
SELECT *, RANK() OVER (ORDER BY column1 DESC) AS rank FROM table_name;

-- DENSE_RANK() - assigns rank without gaps for ties
SELECT *, DENSE_RANK() OVER (ORDER BY column1 DESC) AS dense_rank FROM table_name;

-- PARTITION BY - groups within window function
SELECT *, ROW_NUMBER() OVER (PARTITION BY column1 ORDER BY column2) AS row_num 
FROM table_name;

-- LAG() and LEAD() - access previous/next row
SELECT *, LAG(column1) OVER (ORDER BY id) AS prev_value FROM table_name;
SELECT *, LEAD(column1) OVER (ORDER BY id) AS next_value FROM table_name;

-- Running totals and averages
SELECT *, SUM(column1) OVER (ORDER BY id) AS running_total FROM table_name;
SELECT *, AVG(column1) OVER (ORDER BY id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) 
AS moving_avg FROM table_name;

11. COMMON TABLE EXPRESSIONS (CTEs)
================================================================================

-- Simple CTE
WITH cte_name AS (
    SELECT * FROM table_name WHERE condition
)
SELECT * FROM cte_name;

-- Recursive CTE (for hierarchical data)
WITH RECURSIVE hierarchy AS (
    SELECT id, name, parent_id, 1 AS level FROM table_name WHERE parent_id IS NULL
    UNION ALL
    SELECT t.id, t.name, t.parent_id, h.level + 1 
    FROM table_name t 
    JOIN hierarchy h ON t.parent_id = h.id
)
SELECT * FROM hierarchy;

-- Scenario 1: E-commerce orders
-- Find top 10 customers by total order value
SELECT customer_id, SUM(order_total) as total_spent
FROM orders 
GROUP BY customer_id 
ORDER BY total_spent DESC 
LIMIT 10;

-- Scenario 2: Employee hierarchy
-- Find all employees reporting to a specific manager (recursive)
WITH RECURSIVE employee_hierarchy AS (
    SELECT id, name, manager_id, 1 as level
    FROM employees WHERE manager_id = 1
    UNION ALL
    SELECT e.id, e.name, e.manager_id, eh.level + 1
    FROM employees e
    JOIN employee_hierarchy eh ON e.manager_id = eh.id
)
SELECT * FROM employee_hierarchy;

-- Scenario 3: Sales analysis
-- Monthly sales comparison (current vs previous year)
SELECT 
    MONTH(order_date) as month,
    SUM(CASE WHEN YEAR(order_date) = 2023 THEN amount ELSE 0 END) as current_year,
    SUM(CASE WHEN YEAR(order_date) = 2022 THEN amount ELSE 0 END) as previous_year,
    SUM(CASE WHEN YEAR(order_date) = 2023 THEN amount ELSE 0 END) - 
    SUM(CASE WHEN YEAR(order_date) = 2022 THEN amount ELSE 0 END) as difference
FROM orders
GROUP BY MONTH(order_date)
ORDER BY month;

-- Scenario 4: Data quality check
-- Find records with missing or invalid data
SELECT 'Missing Email' as issue, COUNT(*) as count FROM users WHERE email IS NULL
UNION ALL
SELECT 'Invalid Email Format', COUNT(*) FROM users WHERE email NOT LIKE '%@%.%'
UNION ALL
SELECT 'Negative Age', COUNT(*) FROM users WHERE age < 0;
