ACID (Atomicity, Consistency, Isolation, Durability)

ACID is a set of properties that guarantee reliable database transactions. It ensures data integrity and reliability in database systems, particularly in relational databases (SQL).

1. Atomicity:
   - "All or Nothing" principle
   - Either the entire transaction succeeds, or all changes are rolled back
   - No partial transactions - if any part fails, entire transaction is undone
   - Ensures database never has incomplete or corrupted data
   
   Example:
   - Transfer $100 from Account A to Account B
   - Step 1: Deduct $100 from Account A
   - Step 2: Add $100 to Account B
   - If Step 2 fails, Step 1 is automatically rolled back
   - Result: Either both succeed or both fail (no money lost)

   Real-world: Bank transfer, order processing, booking systems

2. Consistency:
   - Database remains in a valid state before and after transaction
   - All data integrity rules, constraints, and validations are maintained
   - Invalid transactions are rejected, preventing data corruption
   - Referential integrity, foreign keys, check constraints are enforced
   
   Example:
   - Rule: Account balance cannot be negative
   - Transaction tries to withdraw $200 from account with $100
   - Transaction is rejected (consistency violation)
   - Database remains in consistent state

   Real-world: Enforcing business rules, data validation, constraint checking

3. Isolation:
   - Concurrent transactions don't interfere with each other
   - Each transaction sees a consistent snapshot of data
   - Prevents dirty reads, non-repeatable reads, and phantom reads
   - Multiple users can work simultaneously without conflicts
   
   Isolation Levels (from weakest to strongest):
   
   a) Read Uncommitted:
      - Lowest isolation, allows dirty reads
      - Can read uncommitted data from other transactions
      - Rarely used, not recommended
   
   b) Read Committed:
      - Prevents dirty reads
      - Can read only committed data
      - Most common default level
      - May have non-repeatable reads
   
   c) Repeatable Read:
      - Prevents dirty reads and non-repeatable reads
      - Same query returns same results within transaction
      - May still have phantom reads
   
   d) Serializable:
      - Highest isolation level
      - Complete isolation, no interference
      - Transactions execute as if sequentially
      - Prevents all concurrency issues
      - Slower performance due to locking
   
   Example:
   - User A reads account balance: $1000
   - User B transfers $500 (transaction in progress)
   - User A reads again: Still sees $1000 (isolated view)
   - User B commits
   - User A's transaction completes with consistent view

   Real-world: Multi-user systems, concurrent booking, inventory management

4. Durability:
   - Once a transaction is committed, changes are permanent
   - Data survives system crashes, power failures, and restarts
   - Changes are written to persistent storage (disk)
   - No data loss even if system fails immediately after commit
   
   Implementation:
   - Write-Ahead Logging (WAL): Changes logged before commit
   - Transaction logs stored on disk
   - Database recovery uses logs to restore committed transactions
   
   Example:
   - User completes payment transaction
   - Transaction is committed
   - System crashes 1 second later
   - After restart, payment is still recorded (durable)
   - No need to redo the transaction

   Real-world: Financial records, critical data, audit logs

ACID Transaction Example:

BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
  INSERT INTO transaction_log (from_account, to_account, amount) 
  VALUES ('A', 'B', 100);
COMMIT;

If any step fails:
- All changes are rolled back (Atomicity)
- Database remains in valid state (Consistency)
- Other transactions unaffected (Isolation)
- No partial changes saved (Durability)

ACID vs BASE Comparison:

ACID (Traditional SQL Databases):
- Strong consistency: Data is always consistent
- Immediate consistency: Changes are visible immediately
- Best for: Financial transactions, critical data, where accuracy is paramount
- Examples: MySQL, PostgreSQL, Oracle, SQL Server
- Guarantees: Data integrity, reliability, correctness

BASE (NoSQL/Distributed Systems):
- Eventual consistency: Data becomes consistent over time
- High availability: System always responds
- Best for: Large-scale systems, social media, analytics, where availability > immediate consistency
- Examples: Cassandra, DynamoDB, MongoDB (in some configurations)
- Trade-offs: May have stale data, but highly available

When to use ACID:
- Financial transactions (banking, payments)
- Critical data integrity required
- Immediate consistency is mandatory
- Write-heavy with complex relationships
- Banking, healthcare records, inventory management
- E-commerce checkout, booking systems
- Systems where data accuracy > availability

ACID + CAP Theorem Relationship:
- ACID aligns with CP (Consistency + Partition Tolerance) from CAP theorem
- Prioritizes consistency over availability
- During network partitions, system may become unavailable to maintain consistency
- SQL databases typically choose CP: Consistency + Partition Tolerance

ACID Advantages:
- Data integrity guaranteed
- Reliable transactions
- No data corruption
- Predictable behavior
- Strong consistency
- Suitable for critical systems

ACID Disadvantages:
- Harder to scale horizontally
- Potential availability issues during partitions
- Performance overhead (locking, logging)
- Complex distributed transactions
- May block operations for consistency
- Not ideal for high-scale distributed systems

Real-World ACID Examples:

1. Banking System:
   - Money transfer must be atomic (all or nothing)
   - Balance must be consistent (no negative balances)
   - Concurrent transfers must be isolated
   - Transactions must be durable (survive crashes)

2. E-commerce Checkout:
   - Order creation, payment, inventory update must be atomic
   - Stock levels must be consistent
   - Multiple users buying same item must be isolated
   - Orders must be durable

3. Booking System (Airlines, Hotels):
   - Seat/room booking must be atomic
   - Availability must be consistent
   - Concurrent bookings must be isolated
   - Reservations must be durable

4. Healthcare Records:
   - Patient data updates must be atomic
   - Medical records must be consistent
   - Multiple doctors accessing records must be isolated
   - Records must be durable (legal requirement)

Transaction States:
- Active: Transaction is executing
- Partially Committed: All operations completed, but not yet committed
- Committed: Transaction completed successfully, changes are permanent
- Failed: Transaction cannot proceed (error occurred)
- Aborted: Transaction rolled back, database restored to previous state

BASE (Basically Available, Soft state, Eventual consistency)

BASE is a design philosophy used in distributed systems, particularly NoSQL databases, that prioritizes availability and scalability over strict consistency. It's the opposite approach to ACID.

1. Basically Available:
   - System remains available and operational most of the time
   - System responds to every request (even if it's an error or stale data)
   - No single point of failure - if one node fails, others continue working
   - Graceful degradation: system works with reduced functionality during failures
   
   Example: E-commerce site shows cached product prices even if database is temporarily unavailable

2. Soft State:
   - System state can change over time without new input
   - Data can be inconsistent temporarily
   - State is "soft" because it may not be immediately consistent across all nodes
   - State changes propagate asynchronously
   
   Example: User's friend count on social media may show different numbers on different servers temporarily

3. Eventual Consistency:
   - System will become consistent eventually, but not immediately
   - Given enough time, all nodes will have the same data
   - No guarantee of immediate consistency after a write
   - Consistency is achieved over time through replication and synchronization
   
   Example: When you update your profile, it may take a few seconds to appear on all servers

BASE vs ACID Comparison:

ACID (Traditional SQL Databases):
- Strong consistency: Data is always consistent
- Immediate consistency: Changes are visible immediately
- Best for: Financial transactions, critical data, where accuracy is paramount
- Examples: MySQL, PostgreSQL, Oracle

BASE (NoSQL/Distributed Systems):
- Eventual consistency: Data becomes consistent over time
- High availability: System always responds
- Best for: Large-scale systems, social media, analytics, where availability > immediate consistency
- Examples: Cassandra, DynamoDB, MongoDB (in some configurations)

When to use BASE:
- High availability is critical
- System needs to scale horizontally
- Temporary inconsistencies are acceptable
- Read-heavy workloads
- Large-scale distributed systems
- Real-time analytics, social media, content delivery

When to use ACID:
- Financial transactions
- Critical data integrity required
- Immediate consistency is mandatory
- Write-heavy with complex relationships
- Banking, healthcare records, inventory management

BASE + CAP Theorem Relationship:
- BASE aligns with AP (Availability + Partition Tolerance) from CAP theorem
- Sacrifices immediate consistency (C) for availability (A) and partition tolerance (P)
- BASE systems are eventually consistent, which is acceptable for many modern applications

Real-World Examples:

1. Social Media (BASE):
   - User posts appear on different servers at different times
   - Friend count may vary temporarily
   - High availability is more important than immediate consistency

2. E-commerce Product Catalog (BASE):
   - Product prices may be cached differently
   - Inventory counts may be slightly inconsistent
   - System remains available even during database issues

3. Banking System (ACID):
   - Account balance must be immediately consistent
   - Transaction must be atomic and durable
   - Cannot tolerate inconsistencies

4. Content Delivery (BASE):
   - CDN serves cached content
   - Updates propagate eventually
   - High availability for global users

Trade-offs:
- BASE: Better scalability, availability, but may have stale data
- ACID: Strong consistency, but harder to scale, potential availability issues

Modern Approach:
- Many systems use hybrid approach: ACID for critical operations, BASE for non-critical
- Microservices: Each service chooses ACID or BASE based on requirements
- Eventual consistency patterns: Read-your-writes, Monotonic reads, Causal consistency

High Latency (ok to be slow): Email, Reports tools (SAP, Tableau), Background processing tasks (Updates, batch processing)

Mean Latency: Mean latency is like the average response time of a system. It’s calculated by adding up all the response times for requests made to the system and then dividing that total by the number of requests
Ex: Imagine you have data on the time it took for 5 users to load the website: 2 seconds, 3 seconds, 4 seconds, 5 seconds, and 6 seconds.
Add up all the response times: 2 + 3 + 4 + 5 + 6 = 20.
Divide the total by the number of users (which is 5 in this case): 20 ÷ 5 = 4.
So, the mean latency for this example is 4 seconds. It means, on average, it takes 4 seconds for the website to load for these users.

Max latency: is the longest amount of time it takes for a system to respond to a request.
Ex: If the video starts playing for most users within a few seconds, but there’s one user who experiences a delay of 20 seconds before the video starts, then the max latency in this case would be 20 seconds.

High Throughput: Eg: Payment gateways, Social system platforms, search engines,

Rate Limiting: Cap on number of request user can make in a specific window 
Patterns:
1. Fixed Window Pattern
2. Sliding Window Pattern, Leaky Bucket Pattern, Token Bucket Pattern (Common for both)
3. Counter Pattern

Throttling: Control how fast requests sre processed 

1. Token Bucket Pattern (https://www.youtube.com/watch?v=my5dGtncxfw)
    A bucket fills with tokens at a constant rate (e.g., 10 tokens/second), 
    and each request consumes one token - if bucket is empty, request must wait or is rejected.
    When tokens accumulate up to maximum capacity, bucket stops filling until some tokens are consumed.

    Advantages: Handles burst traffic when tokens accumulate, simple to implement, flexible rate limiting.
    Disadvantages: Can overwhelm system with sudden bursts, needs memory to track tokens, not good for strict even distribution. 

2. Leaky Bucket Pattern  (https://www.youtube.com/watch?v=mQCJJqUfn9Y&t=25s)
    Requests flow into bucket at any rate, but exit at fixed constant rate (like water leaking from bucket).
    If bucket is full, new requests are rejected or dropped until space is available.
    Ensures smooth, evenly distributed output rate regardless of input burst traffic.

    Advantages: Prevents traffic bursts from overwhelming system, ensures constant output rate, simple to implement with queue.
    Disadvantages: No burst allowance (strict rate limiting), requests may be dropped when bucket is full, less flexible than token bucket.

3. Fixed Window Pattern 
    Time is divided into fixed windows (e.g., every minute), each window has limit of allowed requests (e.g., 100 requests per minute).
    Counter resets to zero at start of each new window, allowing fresh quota for requests.
    Simple counting mechanism: increment counter for each request, reject requests when counter exceeds window limit.

    Advantages: Very simple to implement with counter and timestamp, easy to understand, memory efficient.
    Disadvantages: Allows burst at window boundary (all requests in last second of window + first second of next), not accurate for precise rate limiting, unfair distribution.

4. Sliding Window Patterns
    Uses a rolling time window that continuously moves forward, tracking requests within current time period (e.g., last 60 seconds).
    Old requests outside the window are discarded, only requests within window count toward the limit.
    More accurate than fixed window because it doesn't allow burst at window boundaries, provides smoother rate limiting.

    Advantages: More accurate rate limiting with no boundary burst problem, better distribution of requests, prevents abuse better than fixed window.
    Disadvantages: More complex to implement (needs timestamp tracking), uses more memory to store request timestamps, computationally expensive to calculate window.

5. Priority Queue Pattern
    Requests are assigned priority levels (high, medium, low), and higher priority requests are processed first regardless of arrival time.
    Uses a priority queue data structure where elements are ordered by priority, not by arrival order.
    Important requests (VIP users, critical operations) get faster service even during high traffic.

    Advantages: Ensures critical requests are handled first, better user experience for priority users, prevents important tasks from being delayed.
    Disadvantages: Lower priority requests may starve (wait indefinitely), more complex to implement, requires defining priority rules.
6. Adaptive Throttling Pattern
7. Circuit Breaker Pattern (Resilience4J)

CAP Theorem  (Brewer's Theorem)
This says any distributed system can only have 2 properties out of 3 

Consistency: 
All nodes see same data at a given time, meaning if one node do write operations then other  nodes are in sync and showing same data back 

Availability:
System remain operational to the response where it can be success or failure, means it never goes down always reponds with some thing 

Partition Tolerance :
System continues working despite network failures, 


CP (Consistency + Partition Tolerance)

Sacrifices: Availability
System becomes unavailable during network partitions
SQL, NoSQL

AP (Availability + Partition Tolerance)
Sacrifices: Consistency
System remains available but may return stale data


CA (Consistency + Availability)
Sacrifices: Partition Tolerance
System only works if there is no network problems 


Example (E-commerce System)

Product Catalog (AP):
- High availability needed
- Temporary inconsistencies acceptable
- Users can see different prices temporarily

--> Social Media, Analytics, Non-critical Data

Shopping Cart (CP):
- Consistency critical
- Can tolerate brief unavailability
- Cart must be accurate

--> Financial Systems, Inventory Management, Login, Critical Data


Payment Processing (CP):
- Consistency absolutely critical
- Cannot have inconsistent payment data
- Availability less important than correctness


Example (Social Media Platform)

User Posts (AP):
- High availability for posting
- Eventual consistency acceptable
- Users can post even if some servers are down

Friend Lists (CP):
- Consistency important
- Cannot have inconsistent friend relationships
- Brief unavailability acceptable

Real-time Chat (AP):
- High availability critical
- Messages can be delivered out of order
- Eventually consistent


CAP + BASE Relationship:

CAP Theorem defines what a distributed system CAN achieve (2 out of 3 properties).
BASE defines HOW a system behaves when choosing Availability + Partition Tolerance (AP).

Connection:
- BASE is the practical implementation of AP (Availability + Partition Tolerance) from CAP
- When you choose AP in CAP, you're essentially choosing a BASE system
- BASE systems sacrifice immediate Consistency (C) for Availability (A) and Partition Tolerance (P)

Mapping:
- CAP: AP (Availability + Partition Tolerance) → BASE philosophy
- CAP: CP (Consistency + Partition Tolerance) → ACID philosophy
- CAP: CA (Consistency + Availability) → Not possible in distributed systems

Example:
- NoSQL databases (Cassandra, DynamoDB) = AP from CAP = BASE approach
- SQL databases (PostgreSQL, MySQL) = CP from CAP = ACID approach

CAP + PACELC Relationship:

PACELC is an extension of CAP theorem that adds more nuance.

PACELC = Partition (P) + Availability (A) vs Consistency (C) + Else (E) + Latency (L) vs Consistency (C)

When there's a Partition (network failure):
- PAC: Same as CAP theorem
- Choose between Availability (A) and Consistency (C)

When there's NO Partition (normal operation):
- ELC: Choose between Latency (L) and Consistency (C)
- Low Latency: Fast responses, eventual consistency (BASE-like)
- High Consistency: Slower responses, immediate consistency (ACID-like)

Key Insight:
- CAP only considers what happens during network partitions
- PACELC also considers normal operation scenarios
- Even without partitions, you must choose between speed (latency) and consistency

Examples:

1. Cassandra (PACELC: PA/EL):
   - Partition: Availability over Consistency (PA)
   - No Partition: Low Latency over Consistency (EL)
   - Fast reads/writes, eventual consistency

2. MongoDB (PACELC: PA/EC):
   - Partition: Availability over Consistency (PA)
   - No Partition: Consistency over Latency (EC)
   - Can be configured for stronger consistency when no partition

3. PostgreSQL (PACELC: PC/EC):
   - Partition: Consistency over Availability (PC)
   - No Partition: Consistency over Latency (EC)
   - Strong consistency, may be slower

Summary:
- CAP: What happens during network failures (2 out of 3)
- BASE: How AP systems behave (Basically Available, Soft state, Eventual consistency)
- PACELC: Extends CAP to also consider normal operation (Latency vs Consistency)

All three help understand trade-offs in distributed systems design.

CQRS (Command Query Responsibility Segregation)

CQRS is an architectural pattern that separates the responsibility of handling commands (writes) and queries (reads) by using different models for reading and writing data. It's based on the principle that read and write operations have different requirements and can be optimized independently.

Command: Operations that change state (Create, Update, Delete)

Query: Operations that retrieve data (Read operations)

Traditional CRUD:
Single Model:
├── User Model
│   ├── Create User
│   ├── Read User
│   ├── Update User
│   └── Delete User
└── Single Database

CQRS Architecture:

Master - Slave 
    Database replication pattern where one master database handles all write operations, and multiple slave databases replicate data and handle read operations.
    Master sends updates to slaves asynchronously, slaves can be used for read scaling and backup purposes.
    If master fails, one slave can be promoted to become new master (with manual intervention or automatic failover).

    Advantages: Simple to implement with clear read/write separation, improves read performance with multiple slaves, provides data redundancy for backup.
    Disadvantages: Single point of failure (master), write bottleneck on master, replication lag can cause stale reads on slaves.

Master - Master 
    Database replication pattern where multiple master databases can handle both read and write operations simultaneously.
    All masters can accept writes and replicate changes to each other, providing high availability and load distribution.
    Requires conflict resolution when same data is modified on different masters at same time.

    Advantages: No single point of failure, writes can be distributed across masters, better availability than master-slave.
    Disadvantages: Complex conflict resolution needed, potential data inconsistency, more complex to implement and maintain.
